# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Mechanica** is a platform for building Vue 3 websites with a visual block editor. Authors write Vue SFC "blocks", an in-page editor arranges them into pages, and pages render server-side (static export, or a future backend). This is the **v2 rewrite** — built ground-up on **Vite 8 / Vue 3.5 / Vitest 4 / Bun**, English throughout, test-covered.

**Repo development runs on Bun** — use `bun`/`bunx`, not `npm`/`node`. **Published packages do not require Bun**: `bun run build` compiles `mechanica-shared` and `mechanica` to `dist/` (plain JS + `.d.ts`), package `exports` point there, and the tarballs ship **`dist/` only** (no `src`), so consumers — Node ≥ 20.19 with npm/pnpm/yarn, or Bun — always run the compiled output. Inside the repo, dev stays live from TS source with no build step: the CLI launcher (`bin/mechanica.js`) runs `src/cli/cli.ts` when it exists (i.e. a repo checkout) under Bun, and `mechanica-shared` resolves to `../shared/src` through tsconfig `paths`, which Bun honors at runtime *ahead of* package `exports` (don't add a `bun` export condition back — it would have to point into `src`, forcing `src` into the tarball). The repo's TS ships extensionless relative imports that only Bun's resolver (or a bundler) handles, never raw Node ESM — dev-app's dev server stays `bunx --bun vite` for exactly that reason.

Current focus is **local development** (the plugin, dev server, and editor). The hosted/SAAS backend is deferred; `mechanica push` still produces a runnable SSR bundle but the deploy/render contract is co-designed later.

## Monorepo layout

Bun workspaces under `packages/*`:

- **`mechanica`** — the published package. Contains the block **compiler** (`src/compiler/`), the **runtime** (`src/core/`), the **Vite plugin** (`src/vite/`), the in-browser **editor** (`src/editor/`), the **CLI** (`src/cli/`), and the standalone **svg-glob** Vite plugin (`src/svg-plugin.ts`). **Dist build** (`bun run build`): `vite.lib.config.ts` builds the browser entries (`index`/`editor`/`composer`/`widgets`) **together** so shared `src/core` modules land in common chunks — one module instance at runtime; splitting them would duplicate the data registry. `?svg-glob` icons compile in (consumers don't register `svgGlob`), `virtual:mechanica/*` stays external, `dist/editor.js` and `dist/composer.js` import the extracted `dist/editor.css`. `vite.node.config.ts` builds `plugin` + `cli` for raw Node. `tsconfig.build.json` emits `dist/types` (it drops the paths-to-source mapping — shared must be built first). dev-app aliases the browser entries back to workspace source in its `vite.config.ts` (+ tsconfig `paths`), so editor/runtime dev stays live with no build.
- **`shared`** (`mechanica-shared`) — DOM-free types, the field-type registry, schema/default helpers, the page-generation (SSG) core (`generate-page.ts`, including the `{{ }}` / raw-JSON `{{{ }}}` HTML templating engine), the SEO helpers (`seo.ts` — `applySeoTags`, `auditPageHtml`, `buildSitemap`/`buildRobotsTxt`; see **SEO** below), and the **`.page.md` page-format codec** (`page-format.ts` — `parsePage`/`serializePage`; see [CONTRACT.md](./CONTRACT.md)). The codec is a separate entry point — `import … from 'mechanica-shared/page-format'`, deliberately **not** re-exported from the barrel: it pulls in the YAML parser, and the barrel is what the client runtime imports, so codec/YAML code must never reach the production bundle (only server-side callers — dev store, CLI, rich-text codec — import the subpath). The codec takes an optional `RichTextCodec` adapter so `richText` fields persist as Markdown `@field` regions on disk but stay `vuewrite` `Block[]` JSON in page state; the adapter (vuewrite-backed) is supplied by the caller — built from block schemas in `mechanica`'s `src/vite/rich-text-codec.ts` (dev server via `ssrLoadModule`, CLI export via its blocks list) — so `shared` stays vuewrite-free. Importable by the runtime and a future render service. **Keep it DOM-free.**
- **`dev-app`** — a playground site that exercises the plugin end to end. Its `.mech/` holds page/data fixtures the user actively edits in the browser; **leave those alone** unless asked.
- **`create-mechanica`** — the `npm create mechanica` / `bun create mechanica` scaffolder. The CLI (`index.js`) is deliberately plain, dependency-free, **Node-compatible JS** (`npm create` runs under Node). It copies the embedded `template/` (a pared-down dev-app: Hero + RichText blocks, head templating, a starter `.page.md`), renames `_gitignore` → `.gitignore` (npm strips real `.gitignore` files on publish), patches the project name, and prints next steps in the invoking package manager's flavor. Scaffolded apps run on plain Node (npm/pnpm/yarn) or Bun. Template deps pin **published** versions, never `workspace:*` — bump them when releasing `mechanica`. Scaffolded apps only install once `mechanica` v2 **and** `mechanica-shared` are on npm (as of 2026-07 npm's `mechanica@latest` is still v1).

## How blocks compile (the core trick)

A block is a Vue SFC whose `<script setup>` calls the global **`defineBlock`** macro (no import). The Vite plugin runs `enforce: 'pre'` and rewrites it at the **source level** (`src/compiler/compile-block.ts`): `defineBlock({...})` → `defineProps([...]) + defineOptions({ blockId, blockSchema })`, then lets `@vitejs/plugin-vue` compile normally. This deliberately avoids v1's string-surgery on plugin-vue's internal `?vue&type=script` request URLs — the thing that pinned v1 to Vite 5. `defineBlock` is the **only** macro; `defineData` / `defineMechanicaApp` / `defineFieldType` are ordinary imported functions. Field types come from `compact-json-schema` with format aliases (`image`, `file`, `color`, `smartLink`, `multiselect`, `richText`) registered in `mechanica-shared`.

Blocks are gathered into the `virtual:mechanica/blocks` module (`src/vite/collect-blocks.ts`).

**The production client build strips the metadata** (`stripMetadata` in `compileBlock` — only `defineProps` remains, no `defineOptions`): schemas and `previewData` feed the editor, the preview route and server-side default-filling, none of which load the client bundle. Dev and the SSR build keep full metadata. Defaults live at the **state level**, never at render time: `generatePage` bakes them into `window.state` at export, and `buildPageState` does the same in dev (`fillContentDefaults` in `pages-store.ts`), so a hand-authored `.page.md` that omits a defaulted prop renders identically in both.

## Block previews & `mechanica shot` (see your work!)

Full user-facing doc: [PREVIEW.md](./PREVIEW.md). The essentials:

A block can declare **`previewData`** in `defineBlock` — example prop values merged over schema defaults (`buildPreviewData` in `mechanica-shared`). It feeds the palette hover preview and the standalone preview route, and doubles as documentation of what the block expects; give every new block meaningful `previewData`.

**Slots preview too:** a `$slots` key in `previewData` fills the block's slots with child blocks — `$slots: { start: [{ blockId: 'card', data: {…} }] }` — each child resolving its own `previewData`/defaults recursively (depth-capped). Slots without authored content render as labelled dashed placeholder boxes, so container/layout blocks are verifiable in shots. The content tree is built by `buildPreviewContent` (`src/core/preview.ts`), shared by the preview route and the palette hover preview.

**`GET /@mechanica/preview/<blockId>?data=<json>`** (dev) renders one block alone — real runtime context + the app's global CSS (the preview entry imports the user's app module without mounting it), site data fetched for `useData`. Readiness/errors are signaled via `window.__MECHANICA_PREVIEW_READY__` / `__MECHANICA_PREVIEW_ERROR__` (`src/core/preview.ts` `mountPreviewApp`, entry in `src/vite/entries.ts`, route in `src/vite/dev/preview.ts`).

**`mechanica shot <blockId>`** (from `dev-app`: `bun ../mechanica/bin/mechanica.js shot <blockId>`) screenshots that route headless and prints the PNG path plus any console/render errors. Flags: `--data <json|@file>`, `--width 1440,768,390`, `--out <path>`, `--server <url>`, `--browser <path>`, `--full`. Output defaults to `.mech/shots/` (gitignored). It reuses a running dev server (much faster — keep `bun run dev` running while iterating) or boots an ephemeral one, and drives a system Edge/Chrome over **raw CDP on the native WebSocket** (`src/cli/shot.ts`) — deliberately no Playwright/Puppeteer: their launch handshake uses Node-only fd pipes that hang under Bun.

**`mechanica shot </page/path>`** (a target starting with `/`, or `--page </path>`) screenshots a **whole page** instead: the real dev page with the editor overlay stripped (`?mechanica-shot` skips the `mechanica/editor` import in `transformIndexHtml`), full-page capture, page existence validated against the store (unknown paths fail listing the real ones). Use it to verify `.page.md` compositions — block spacing, shared data flowing in, `{{ }}` head templating.

**`mechanica thumbs [/prefix]`** walks every page (or those under a prefix) and writes 480px-wide top-of-page thumbnails (clipped to the page's real height, max 2000px of page) to `.mech/thumbs/` (gitignored), which the dev middleware serves at `/@mechanica/thumbs/<slug>.png` and `PagesDialog` shows in its side preview panel (monogram fallback when missing). **`mechanica thumbs --blocks [id]`** does the same for blocks: every palette-visible block renders through the preview route into `.mech/thumbs/blocks/<blockId>.png` (240px wide, clipped to the block's height), and the palette shows them on its cards (icon/monogram fallback). The block list comes from `GET /@mechanica/blocks`. A mostly-empty block thumbnail usually means missing `previewData`. Manual regeneration by design — run both after a content/styling session. Browser/CDP plumbing shared by all commands lives in `src/cli/headless.ts`.

**After creating or visually changing a block, run `mechanica shot <blockId>`; after authoring or editing a `.page.md`, run `mechanica shot </its/path>` — and Read the PNG before considering the work done.** Check spacing, overflow, and responsive behavior (`--width 1440,390`).

## Runtime, modes, and entries

State shape: `State { content: ContentBlock[], data, query, page }` (in `mechanica-shared`). `createMechanica` provides a `MechanicaContext` (content / data / blocks / router / query / page) via `inject`. The runtime is **mode-aware via context** (`'client' | 'server' | 'dev'`) — there is **no `import.meta.env` branching** (a deliberate departure from v1).

The user exports `defineMechanicaApp({ root })`; the plugin generates entries (`src/vite/entries.ts`):
- `virtual:mechanica/client` → `createMechanicaApp(def, { mode, state, blocks }).mount('#app')`
- the SSR entry exports `render(state)` / `blocksList` / `dataEntries` (used by `mechanica export` and the future backend).

`mechanica build` runs two Vite builds; the SSR build writes the generated entry to a **real temp file** because rolldown (Vite 8's bundler) can't use a `\0`-virtual module as a build entry.

**Blocks are code-split in the client build** (dev + SSR stay eager): `virtual:mechanica/blocks` becomes a `blockLoaders` map of dynamic imports, the generated entry awaits only the blocks `window.state.content` uses (`loadBlocks` in `src/core/load-blocks.ts`) before mounting, and the router's `ensureBlocks` hook loads missing chunks before SPA content swaps. **Chunking is manual, not heuristic** (plugin option `blockChunks`): by default all blocks bundle into one `blocks` chunk + CSS file (`'bundled'` — one request, cached across pages, separate from the entry so editing a block never invalidates the Vue/runtime chunk); `'per-block'` restores one chunk per block. Either way, `chunk: '<name>'` in `defineBlock` carves the marked blocks into their own `blocks-<name>` chunk — use it for heavy, rarely-used blocks (see dev-app's rich-text blocks, which keep vuewrite off other pages). The plugin implements this as a rolldown `codeSplitting` group whose `name` callback walks each module's importers: a dependency folds into a blocks chunk only when *every* import path leads to blocks of that one group, so block-only helpers/libs ride along while anything the entry shares (Vue) stays put. The plugin emits `dist/mechanica-blocks.json` (blockId → `{ src, chunk }` — the containing output chunk, since bundled blocks have no per-block manifest keys) and the build enables Vite's manifest; `mechanica export` joins them by chunk file (`src/cli/page-assets.ts`) to inject per-page `<link rel="stylesheet">` + `<link rel="modulepreload">` tags, so each exported page loads exactly its own blocks' code with no extra round trip or unstyled flash.

## Layouts & standalone page blocks

**A layout is a page's shell, chosen per page in core** (not via `defineData` — that userland pattern predates this). `defineMechanicaApp({ root, layouts: { site: SiteLayout, docs: DocsLayout } })` declares named layout components, each rendering `<Content/>` inside its own chrome; the root renders the core **`<Layout/>`** component (`src/core/layout.ts`), which picks by `state.page.layout` — reactive across SPA navigation and in-editor page switches (keyed by name, so switching remounts the shell cleanly). The **first map entry is the default**; no `layouts` declared → `<Layout/>` ≡ `<Content/>`. A page opts in with top-level **`layout: docs`** frontmatter (`PageDoc.layout`, spec in CONTRACT.md); `VirtualPage.layout` does the same for generated pages. `useLayout()` (barrel-exported) gives `{ name, names }`. The layout rides `state.page.layout` in dev *and* export (SSR renders through it, hydration matches), and is **base-owned** under i18n — translations always inherit it, `savePage` ignores the layout patch on translation saves. Reference: dev-app's `src/layouts/` (`site` + `bare`) and `.mech/pages/404.page.md`.

**Editor surface — the "Page setup" pane, not a sidebar control.** Layout (and the page block, below) are set-once page properties, unlike the locale (switched constantly to compare translations) — so they live in the Page data dialog: a pinned **Page setup** rail entry (`components/PageSettings.vue`, present only when the app offers ≥2 layouts or standalone blocks; the "Page data" toolbar button shows whenever the dialog has *any* section). Layout renders as **radio cards** (every option visible, the first tagged "Default"; picking it clears the frontmatter key; locked with a note while editing a translation — names come off the runtime bridge's `layoutNames`). Changes are undoable, ride the normal save, and live-swap the shell via a page-meta push (only pushed when the layout actually changed — replacing page meta per keystroke would ripple). In **PagesDialog** the layout surfaces only as a quiet chip in the hover **preview panel caption**, and only for pages carrying an explicit `layout:` (`listPages` reports `layout`; default-layout pages show nothing — rows stay clean).

**Standalone blocks** are whole-page blocks (a feedback form, a 404, a legal page): `standalone: true` in `defineBlock` offers them in the empty page’s **"Start this page" palette group** (led by the dashed "Design this page" card) — they never pollute the palette on pages with content (placed blocks always render; dev-app reference: `NotFound.vue`). The Page setup pane also offers them as a **"Page block" select**: picking one *becomes the page’s entire content* — silently on an empty page or when swapping one standalone block for another, behind a confirm when replacing hand-arranged blocks (pure logic in `editor/lib/page-setup.ts` — `standalonePageBlockId`/`applyPageBlock`; everything is undoable). **`layouts: ['docs']`** on `defineBlock` is a palette filter like `folders` — the block is only offered on pages whose effective layout matches (`blockAvailableForLayout` in `editor/lib/block-meta.ts`; ignored on sites without layouts). Composed blocks can be standalone too — a **"Whole-page block"** switch in the composer settings (`ComposedBlockDefinition.standalone`, codec-round-tripped like `hidden`), so a designer-built 404/coming-soon reaches "Start this page" and the Page-block select. The editor store keeps `hidden` blocks in `blocks`/`blocksById` (placed hidden blocks need names/settings/slots) — **the palette does the filtering**, not the store.

**One-off page designs in the composer:** an empty page's palette offers **"Design this page"** — it creates a composed block named after the page with **`hidden: true`** (`ComposedBlockDefinition.hidden`, round-tripped by the `block-format` codec, filtered from the palette and from `mechanica thumbs --blocks`), places it as the page's sole content, and opens the composer on it. The block toolbar shows **Edit in the composer** for any placed composed block (replacing "Save as reusable block" there) — the entry point for palette-hidden blocks. Composer settings gained a **"Show in palette"** toggle (`setMeta({ hidden })`) — ticking it promotes a one-off design to a reusable "Site blocks" entry.

## Dev server & the `.mech/` store

The plugin's `configureServer` mounts the `/@mechanica` middleware (`src/vite/dev/`) over the project's `.mech/` directory:
- `pages-store.ts` — page CRUD (`createPage`, `savePage`, `renamePage`, `duplicatePage`, `deletePage`, `listPages`, folders). Pages live at `.mech/pages/**.page.md` — a human-readable, Markdown-centric format authored primarily by Claude (`mechanica-shared`'s `parsePage`/`serializePage`; spec in [CONTRACT.md](./CONTRACT.md)). The editor still talks JSON over the wire; only the on-disk codec is `.page.md`. Site/folder shared data (`data.json`, `folders.json`) stay JSON.
- `data-store.ts` — scoped shared data (see **Data scoping** below).
- `assets-store.ts` — uploads → `.mech/assets`, plus the **image manifest** (`.mech/images.json`: per-asset `width`/`height` + LQIP `previewSrc`; see **SEO**). `query-dev.ts`, `middleware.ts`.

`transformIndexHtml` injects `window.state` + the client entry + `mechanica/editor` in dev (client entry only in build), and runs the `{{ }}` templating engine over `index.html` so dev matches the build (see **Page `<head>`**).

## The editor (`src/editor/`)

An in-page overlay app. `createMechanica` exposes the live runtime through a versioned **bridge** (`lib/bridge.ts`); the editor pushes edits for live preview and debounce-saves to `/@mechanica/save`. The store **clones** incoming `window.state` so it never shares mutable references with the runtime (sharing caused a typing-flicker bug — keep it cloned). Folder layout:

- **`lib/`** — non-Vue logic: `store.ts` (reactive editor store), `content-tree.ts` (tree ops + slot nesting), `drag-controller.ts` (pointer DnD), `history.ts` (undo/redo), `shortcuts.ts`, `block-meta.ts`, `use-block-frames.ts`, `page-list.ts`, `bridge.ts`, `types.ts`. Pure helpers here are unit-tested.
- **`components/`** — panels: `BlockPalette`, `HierarchyTree`, `BlockSettings`, `DataSettings`, `BlockFrame`, `PageBar`, and the **`VIcon`** component.
- **`ui/`** — the dialog system: `dialog.ts` (`createDialogStore` / `useDialog`, a stack), `VDialogHost.vue` (teleports to body, backdrop + capture-phase Escape), `VDialog.vue` (modal shell: `standard` / `wide`).
- **`dialogs/`** — dialog contents: `PagesDialog` (page browser), `DataDialog` (page data), `RichTextDialog` (rich text in a window).
- **`props-panel/`** — recursive schema form: `SchemaForm` / `SchemaField` / `ArrayField`.
- **`fields/`** — the field-editor registry (`defineFieldType` / `registerFields`) and editors (string, text, number, boolean, color, image, smartLink, multiselect, richText). The `richText` editor is `fields/richtext/RichTextEditor.vue`: a `vuewrite`-based UI (toolbar — block type + B/I/U — plus Markdown shortcuts) with a **WYSIWYG ⇄ Markdown switch** (`vuewrite/markdown`), used by both the inline field and the roomy `RichTextDialog`; `fields/richtext/config.ts` holds the shared renderer/decorator (the dev-app `RichText` viewer block mirrors it).
- **`styles/`**, **`icons/`** — see below.
- `EditorApp.vue` (shell) and `editor.ts` (dev entry) stay at the root.

**Rich-text widgets** (`fields/richtext/widgets.ts`): blocks that flow *inside prose* — built-ins image/code/callout/table, plus site-defined ones. A site declares a widget with **`defineWidget`** (imported from **`mechanica/widgets`**) in `src/widgets/*.ts` (plugin option `widgetsDir`); the plugin collects them into `virtual:mechanica/widgets`, imported **only by the editor entry**, so widget editing UIs never reach the site build. A widget is `{ type, title, icon, keywords?, create(), editor? }` — `icon` is a built-in VIcon name or a raw `<svg>` string (colors normalized to `currentColor`); the `editor` component receives `block` (mutate it directly), emits `change` to land in undo history, gets uploads/image-picking via `useWidgetServices()`, and renders behind an error boundary (a broken widget shows an inert chip, never kills the editor). On disk, widgets ride `vuewrite/markdown`'s generic forms (`<type attr="…"/>`, `:::type` fences) — keep extra block fields flat strings/booleans. Page rendering stays in user land: a `#<type>` slot on the site's `TextViewer` (see dev-app's `RichTextView.vue` + `src/widgets/cta-button.widget.ts` for the full pattern). The **table** widget wraps `vuewrite/table`'s `TableEditor` (`RichTableWidget.vue`; persists as a GFM pipe table, header row first, cells keep inline styles) — it gets the hosting editor's ref via the internal `richTextEditorRefKey` provide so cell edits push history and Delete removes the block; sites render tables with `TableViewer` in their `#table` slot (structural CSS from `vuewrite/style.css`, themed via the `--vw-table-*` custom properties on `.vw-table`, per side). In the editor, widget slots must spread the slot's `props` onto their wrapper — that's what carries `data-vw-block-id`, without which vuewrite selection (and block deletion) can't target the widget.

**Rich-text context menus** (the shared `contextMenuKey` controller + `VContextMenu`): right-clicking a block in the rich-text field offers Add paragraph above/below, Move up/down, Duplicate, Delete block — the reliable way to manage `editable: false` widgets the keyboard can't always reach. Right-clicking a table cell gets table actions instead (insert row/column at the click point, per-column alignment with a check mark, delete row/column/table) via `TableEditor`'s `contextmenu` emit — the widget stops propagation so the block menu doesn't also open. Right-clicks inside widget-owned form controls (e.g. the code widget's textarea) keep the native browser menu.

**Page management:** `PageBar` (sidebar) shows the current page and opens `PagesDialog` — a searchable table (name/path columns, no inline thumbnails) with a folder rail on the left and a **preview panel floating beside the dialog** showing the hovered/keyboard-highlighted page's thumbnail (hidden under ~1160px viewports). Search is global (it ignores the folder filter), arrow keys + Enter navigate from the search box, and rows offer Rename / Duplicate / Delete via hover icons or right-click context menu. Create/rename/duplicate go through `PageFormDialog` — a small stacked dialog whose path auto-follows the name (`pathFromName`, folder-prefixed) until the path is edited by hand. There is no `<select>` dropdown and no ambient "current page" actions.

**Links on the live page are followable:** clicking a link inside a block follows it instead of selecting the block — internal links go through the editor's in-place page switch (`use-block-frames.ts` `linkClickAction` + `navigation.switchPage`), so the save path, page version and undo history move with the page; modified clicks, `target="_blank"`, downloads, external and same-page hash links keep native browser behavior. Blocks are selected by clicking non-link areas (or the hierarchy tree). Saves target the state's `page.path`, never the raw URL — on a paginated variant URL (`/blog/2`) edits save to the base page.

`vuesix` and `vuewrite` are the **user's own** libraries. `vuesix` is composables/utilities only (no UI components); `vuewrite` provides the `TextEditor` for rich text.

## The Block Composer (composed blocks)

(The Figma-grade v2 UX — R1–R5 — is implemented; its design doc COMPOSER-REDESIGN.md, like PLAN.md, has since been removed from the repo.) A **composed block** is **data, not code** — a named, parameterized `ContentBlock` subtree that *expands* through the normal `renderBlocks` pipeline at render time (no compilation), so it previews, exports and screenshots exactly like a compiled block. The entity is `ComposedBlockDefinition` (`mechanica-shared`); files are `.mech/blocks/<id>.block.yml` (codec `mechanica-shared/block-format` — a subpath, YAML, kept off the barrel like `page-format`); the runtime factory is `createComposedComponent` (`src/core/composed.ts`). Definitions are collected into `virtual:mechanica/composed` (`src/vite/collect-composed.ts`) and registered by `createMechanica` alongside the **layout/content elements** — `mech:frame` / `mech:text` / `mech:image` (`src/elements/`, plain render fns, always shipped; **no `mech:button`** — a button's look is a design-system decision, so sites ship their own). The composed block **is a root frame**: in the editor `def.template` is always exactly one `mech:frame` (`lib/normalize-template.ts`, enforced in the store; the runtime still tolerates any template). Responsive is CSS-variable indirection: elements set inline `--el-*` / `--el-*-md` / `--el-*-sm` and the **generated** `virtual:mechanica/elements.css` (`src/elements/emit-css.ts` — generated per-site because the breakpoint widths are configurable; `elements.scss` keeps only the `@property` registrations + structural rules) has the media queries that pick which var to read (`$bp` overrides, cascade sm ← md ← base); **every element knob rides the vars — layout *and* visual style** (frame fill/radius/min-height/shadow, text size/weight/line-height/color, image fit/ratio/radius; specs in `style-vars.ts` `FRAME_VARS`/`TEXT_VARS`/`IMAGE_VARS`), so all of them take per-breakpoint overrides — never emit a data knob as a direct inline style, it would beat the media queries; typography falls back through `var(…, revert)` so unset knobs keep UA/site styles (CSS-wide keywords in var() fallbacks: 2023+ browsers, same era as the `@property` dependency); only the compound no-UI knobs (frame `overflow`, `border*`) and `$abs` stay inline base-only. The `--el-*` vars are registered `@property { inherits: false }` (top of `elements.scss`) so a parent's inline value — e.g. a frame's `margin`, set only when present — never cascades onto its children; `maxWidth` (`--el-maxw` + `margin-inline:auto`) gives the full-bleed-bg + centered-content-column pattern; `$abs` maps to absolute placement; `margin` (`--el-margin`) is an element/placement knob (padding shorthand forms, negatives allowed); `{ $bind: 'prop' }` values resolve from the placed instance's props (dot-paths reach into object props: `$bind: 'cta.url'`). **Element capabilities beyond layout:** frames and texts take a **`link`** (a smartLink value — a linked frame renders as the runtime `<Link>`, i.e. a real `<a>` with SPA/locale handling, attrs falling through so class/style/`data-block-id` land on the anchor; a linked text keeps its tag and wraps its content in the anchor; `a.mxel-frame` / `.mxel-text a` inherit color/decoration so linking never restyles — behavior, not styling). **`hide`** is per-breakpoint visibility riding the same var trick (`--el-display`, kind-default fallbacks; `hide: true` in `$bp.sm` = "hide on mobile", an explicit `false` un-hides at a breakpoint). A frame's Fill also takes a **background image**: `bgImage` (an image-field-shaped object — one data key emits `--el-bgimg` + `--el-bgpos` from its focal point; a VarSpec may be an array) plus a `bgOverlay` color that `emit-css.ts` composes as a same-color `linear-gradient` over the url — its bindings sit *after* the `background` shorthand so color + image coexist; `background-size: cover` is scoped to frames that set the var. **Repeat (`$each`):** a template node with `$each: 'items'` expands once per item of that array prop (`resolveList` in `shared`'s `compose.ts`) — inside the subtree `$bind: '$item'` / `'$item.field'` / `'$index'` resolve from the current item (nested `$each` shadows `$item`), ids gain an `@<i>` suffix, and a missing/empty prop renders nothing. **Placement wrapper:** built-in elements apply their own `margin`/`hide`/`$abs` inline, but a placed **component / composed block** (an SFC whose root we can't style) that carries `margin`, `hide` or `$abs` is wrapped by `renderBlocks` in a `.mxel mxel-slot` positioning div that owns the placement style + the editor `data-block-id` (those keys are stripped from the component's props — they're layout, never component props). This is how the composer offers **Margin + Visibility + Repeat + Position on components too** (`placementStyle` in `elements/style-vars.ts`; the wrap fires only for non-`mech:` blocks with placement data, so page blocks are untouched). `mechanica export` rewrites uploaded-asset URLs *inside composed templates* (`mech:image` src, `bgImage`) the way `collectFiles` rewrites page data — `rewriteComposedAssets` in `cli/export.ts` mutates `ssr.composedList` in place (the same objects the SSR runtime renders from). Dev CRUD lives in `src/vite/dev/composed-store.ts` behind `/@mechanica/composed*`.

**Composer manifest** (the designer↔developer bridge, `defineComposer` in `src/composer.ts`, plugin option `composerFile`; full spec [COMPOSER-MANIFEST.md](./COMPOSER-MANIFEST.md)): one home for the site's design system as the composer sees it — `components`, `classes`, `breakpoints` (all optional; `defineComposerComponents` was the components-only predecessor). **Components**: a plain Vue SFC + compact-json-schema for its props (a bare string re-exposes a compiled block by id). The plugin collects the manifest into `virtual:mechanica/components` (`src/vite/collect-components.ts`) exporting `registerComponents`/`componentDefs`/`classDefs`; **every generated entry** (client/ssr/preview/composer) calls `registerComponents(blocks)`, so composed blocks that place a component render in dev, SSR, export and the preview/`shot` route. In the composer they appear in a **Components** palette; props are editable *and* ⚡-bindable (`ComponentFields.vue`). **Classes**: real site CSS classes (the manifest key *is* the class name) offered as element **Style** selects in the inspector — pick "Container" on a frame and it gets the site's `.container` (data key `cls`, space-separated, base-only, sanitized, appended by the element renderers; `on: 'frame'|'text'|'image'` filters which kinds see it). A class may declare a **`group`**: same group = mutually exclusive (one single-pick select each, labelled by the humanized key), different groups **stack** (a frame can be Container + Panel at once); ungrouped classes share one implicit "Style" select. This is the Figma model (separate fill/text/effect styles), not Webflow's flat combo list — the dev guarantees groups are orthogonal so precedence stays clear. Pure grouping/replace logic in `editor/composer/lib/class-groups.ts`. **Each Style dropdown previews what a class does**: hovering an option shows a pane (left of the list) with the class's real selector (`.ds-container`) + its CSS declarations, read live from the CSSOM (`class-css.ts` → the `#option-hint` slot on `VSelect`) — the base `.class` rule's authored shorthands with `var()` resolved against `:root` (`max-width: var(--container) → 1140px`); editor-only, cross-origin + pseudo/`@media` rules skipped. The cascade lets a class win while a set knob still wins over the class: the yield-prop floors sit in `@layer mechanica` (any author class outranks them) and each yields to an unlayered `.mxel-*[style*='--el-x:']` knob rung; structural/flex props (`w/h/grow/self/dir/align/justify/wrap`) stay hard floors classes can't touch — all in `emit-css.ts`. **Breakpoints** `{ md, sm }` (max-widths, numeric literals only): read *statically* from the manifest source by the plugin (`read-breakpoints.ts` — it can't evaluate the SFC-importing module) and fed to `emitElementsCss` (media-query widths) + the composer entry (device switcher / banner). `normalizeClassManifest` (`mechanica-shared`) unfolds the class shorthands; it's re-exported from `mechanica` so the generated components module can import it (a virtual module can't resolve bare `mechanica-shared` in the source-aliased dev app).

The **Composer UI** (`src/editor/composer/`, exported as `mechanica/composer`) is a full-screen dev app at `/@mechanica/composer/<id>` (or `~new`): a **top toolbar** inserts Row/Column/Text/Image (icon buttons) + a **Components** popover (`InsertToolbar.vue`; R/C/T/I keys also arm insertion) — drag a card onto the canvas or click to append; the **left panel is the layers tree** (drag to reorder/reparent); the **right panel** is `ComposerInspector` when something is selected, else `ComposerSettings` (Name/Category/Icon + the compact **Variables** rows + "Edit root layout"). The inspector shows a **slim core** (Size + Layout for frames; Content + Typography for text) built from Figma-style primitives — `NumInput`/`SizeInput` (Hug·Fill·Fixed via `VSelect` + measured px), 3×3 `AlignGrid` (calm dots by default — accent dot marks the active alignment — with a Figma-style three-stripe preview on the *hovered* cell: horizontal bars for column frames, vertical for row, aligned by `align`/`justify`), icon `SegControl`, token-first `ColorField` — and everything else is an **optional property** in a **Properties** section (`lib/inspector-props.ts` registry + store `addProp`/`removeProp`/`hasProp`): Padding, Margin (an element capability — `--el-margin`, same shorthand forms as padding, negatives allowed, per-side math in `lib/padding.ts`), **Limits** (min/max width & height as a compact 2×2 grid — dimension rows × Min/Max columns, drag-scrub fields with `0`/`None` default-hint placeholders; in breakpoint mode each field that carries an override is tinted accent — `NumInput`'s `overridden` prop — so the grid shows *which* limit differs, with the section header's reset clearing them all; `--el-minw`/`--el-maxw`/`--el-minh`/`--el-maxh`, breakpoint-capable, on all kinds; `maxWidth` on a frame also centers it — the content-column pattern, so there's no separate "Content width" control; the root seeds `minHeight` so it's never zero-height), Fill, Radius, and Position — a 3×3 `AnchorGrid` pin-point over the nine `$abs` anchors (four corners, four edge-centres, centre — decomposed via the shared `ANCHOR_H`/`ANCHOR_V` maps in `elements/style-vars.ts`, applied by `absStyle`) + offset fields named for the pinned edge (Left/Right/Top/Bottom, `lib/abs.ts` `absAxisLabels`; not offered on the root; switching it on *is* `$abs`). Since a right-/bottom-pinned offset maps to CSS `right:`/`bottom:` (grows away from the pointer), on-canvas dragging inverts that axis (`anchorSigns`) and switching anchor re-expresses the offsets so the element stays visually put (`reanchorOffset`, fed a DOM measurement of the element vs its containing block). Each is a **`PropToggle` switch row** (not an add menu): every property a node *can* carry is listed, and flipping one on activates it and expands its editor beneath while flipping off deletes the key from every layer. A property reads as on when its data already exists (base or any `$bp` layer) or it was switched on this session; switching on writes no data until the first edit. Padding + Margin edit through **`BoxSideInput`** — a box-model control that lays the four side fields where they act (top on top, left on the left…) around a glyph standing in for the element, so position *is* the label; the fields are drag-to-scrub, and holding **Alt** mirrors an edit to the opposite side (top↔bottom, left↔right) — in the box (`setSide(..., symmetric)`) and on the canvas padding strips, where the opposite strip highlights (`is-mirror`) while it changes. Hovering or editing a side also **echoes it on the canvas** (`store.spacing` → `CanvasOverlay`): padding lights the matching inset strip blue (`is-echo`), margin paints a translucent-orange outset region (`marginRegion`) outside the element, and the frame's **Gap** field lights the gap strips between children pink — three visibly different kinds of space; with **Alt** held the padding/margin echo covers both the side and its opposite (`symmetric`), matching what an Alt edit would change. Touching the **Position** control marks the `$abs` **align point** — the anchor's reference point on the parent, from which the offset is measured (a ring), with dashed offset guides to the element's matching anchor point (`anchorPoint`). **Breakpoint styling** is a mode, not a panel: the top-bar **device switcher** (desktop/tablet/mobile icons; md ≤ 1024px, sm ≤ 640px) resizes + re-fits the canvas *and* flips the inspector into override editing — every style edit writes to that `$bp` layer (`setData(…, { responsive: true })`, position/content/tag/src stay base = shared), values display effective-at-breakpoint (`effectiveData` pre-merges for the canvas, since the canvas width isn't the viewport width), an overridden row gets a blue ↩ reset (`OverrideLabel`; `PropToggle` rows carry the same), a blue banner atop the right panel names the mode + scope with an exit, and the Tablet/Mobile bar buttons show a dot when the block defines overrides there. A **placed component / composed block** gets the same Properties switches but only the placement props — **Margin + Visibility + Repeat + Position** — since those attach to its render wrapper, not the component's internals (`availableProps(..., isComponent)`). The newer switches: **Fill** grows an image half (upload/replace, a 3×3 `AnchorGrid` doubling as the focal-point picker via the shared `ANCHOR_H`/`ANCHOR_V` maps, an Overlay `ColorField`; dataKeys `background`/`bgImage`/`bgOverlay`); **Link** hosts the page editor's `SmartLinkField` (base-only — a link is behavior, not responsive style) and is ⚡-bindable like any field; **Visibility** is a Shown/Hidden `SegControl` writing `hide` to the active `$bp` layer ("Shown" at base deletes the key), with hidden nodes dimmed in the layers tree + an eye-off button there to un-hide (the canvas honors `hide`, so the tree is where a hidden node stays reachable); **Repeat** routes through store `setEach` (on: creates a unique array prop + 3 preview items + `$each`; off: restores `$item.*` bindings from the first preview item and drops the prop unless another node repeats over it) and shows the prop name (rename follows `$each` keys too) + a preview-count field (`setEachCount`, clamped 1–12). Inside a repeated subtree the ⚡ on any field exposes a **per-item field** instead — `exposeProp` detects the nearest `$each` scope (self-first), writes `$bind: '$item.<field>'`, adds the field to the array prop's `items.properties`, seeds every preview item with the current value, and mirrors the preview list into the prop's `default` so freshly placed instances start with the example items; the bind chip shows the field name with a repeat icon, and its ✕ goes through `unbindField` (restores the first item's value, prunes the field when nothing else in that scope binds it). On canvas `resolveForCanvas` renders every preview item — the first instance keeps the template node's id, ghosts ride an `@<i>` suffix that every DOM hit (select/hover/dblclick/marquee/drop) normalizes back via `templateNodeId`, so clicking any instance edits the one template node. The **canvas** is a pannable/zoomable dot-grid viewport (`.mech-composer__world` = `translate(panX,panY) scale(zoom)`; pan = middle-drag/two-finger, zoom = Ctrl/pinch wheel; floating zoom bar; view state on the store root, not saved/undone; math in `lib/canvas-view.ts`). **The world *is* the artboard** — there is no separate white "canvas" underlay: the world carries the device width (inline) + the artboard card shadow, and the root frame (which defaults to `w: 'fill'` + a white `background` + a `minHeight` floor in `createRootFrame`) fills it and *is* the visible surface. So the root block is the sized thing; a short block no longer shows an oversized backing behind it, and the drop-target / marquee resolve against `.mech-composer__world` (the root fills it, so an in-bounds pointer hits the root directly). **On-canvas direct manipulation** (`CanvasOverlay.vue` + pure `lib/canvas-overlay.ts`): hover outline, 2px selection frame, 8 resize handles, size badge, frame label — **resize** (drag handle → Fixed; double-click → Hug), **move** (drag an element → relocate via the shared `lib/canvas-drop-target.ts`, same indicator/ghost as insert), **`$abs` free drag**, and **double-click a text to edit it inline**; the measured size feeds `SizeInput`; `history.commit()` on drag end coalesces one undo entry. **Multi-select** (store `selectedIds`, primary = last): shift/⌘-click on canvas or in the layers tree toggles membership, an empty-canvas **rubber-band marquee** (`lib/marquee.ts`) selects intersecting children, the overlay draws a frame per element + a dashed union box (resize handles only when one is selected), an all-`$abs` selection group-drags together, and `Delete`/`⌘D` act on the whole set via a **`MultiSelectPanel`**. Composer + editor keyboard shortcuts are keyboard-layout-independent (`editor/lib/keyboard.ts` `shortcutChar` prefers a Latin `event.key`, else falls back to the physical `event.code`, so Cyrillic/Greek/etc. layouts still trigger them). Composed blocks appear in the **page editor palette** under "Site blocks" (`Block.composed`) with **New block** + Edit/Delete; the page block toolbar has **Save as reusable block** (`saveAsBlock`). After changing a composed block, `mechanica shot <id>` and `mechanica thumbs --blocks` cover it. **`bun run build` before export/pack** — the `block-format` subpath, `composer` entry and `virtual:mechanica/components` wiring are dist/plugin concerns. Only the **browser entries** (runtime/editor/composer) are source-aliased in dev-app, so those edits are live; the **Vite plugin resolves from `dist/`** (Vite's config loader uses the `import` condition, not `bun`), so any Node-side change — `src/vite/*` (plugin, entries, `collect-*`, `read-breakpoints`), `src/elements/emit-css.ts`, the CLI — needs **`bun run build` + a dev-server restart** to take effect.

## Styling (Sass design system)

Light theme only, modern, with **black pill primary buttons** — based on the legacy look, modernized. **Use Sass.** Design tokens are CSS custom properties (`--mech-*`) in `styles/_variables.scss`. Shared primitives + editor chrome live in `styles/editor.scss` (`.mech-button` neutral, `.mech-button.is-primary` black, inputs, tabs, frames, toolbar, drag indicators). **Component-specific styles go in the component** as `<style lang="scss" scoped>` (PageBar, PagesDialog, HierarchyTree, BlockPalette, DataSettings, the dialogs, …). Consume tokens via `var(--mech-*)` — no per-file `@use` needed. Don't reintroduce a dark theme without being asked.

## Icons (VIcon + svg-glob)

Icons are individual `*.svg` files under `src/editor/icons/`, bundled as raw strings by the **`?svg-glob`** Vite plugin (`src/svg-plugin.ts`), which normalizes hard-coded colors to `currentColor` and strips `xmlns`. `VIcon.vue` imports `../icons?svg-glob` and renders `<VIcon name="filename" />`. **To add an icon:** drop a `*.svg` in `icons/` (e.g. a Figma export) and reference it by filename; size it via CSS (`.vicon` defaults to `1em`). The plugin is registered in `dev-app/vite.config.ts` and **both** projects of `packages/mechanica/vitest.config.ts` (DOM tests render real icons), and re-exported as `svgGlob` from `mechanica/plugin`. There is a `*?svg-glob` type shim in `src/vue-shim.d.ts`.

## Page `<head>` metadata (defineData + templating, not a panel)

Per-page `<head>` (title, description, Open Graph, any tag) is **ordinary data**, not a bespoke editor concept. Define a **page-scoped `defineData`** entry (e.g. `head` with `title`/`description`) and template it into `index.html` with `{{ head.title }}` placeholders. The engine is `passDataToHTML` in `mechanica-shared` (HTML-escapes resolved values); it runs at **build** (`generatePage`) and in **dev** (`transformIndexHtml`), so the two match. `{{ page.path }}` and `{{ site.url }}` / `{{ site.name }}` (from the plugin's `siteUrl` / `siteName` options) also work. The triple-brace form `{{{ expr }}}` emits raw script-safe JSON instead of HTML-escaped text — for hand-wired JSON-LD (`Article`, `Product`) inside a `<script type="application/ld+json">`. Small landing pages can just hardcode their `<head>`. Edit the values in the editor's **Page data** window. (`updatePageMeta` was removed; `renamePage` only changes a page's editor label.)

## SEO (automatic at export)

Set **`siteUrl`** (and optionally `siteName`) on the plugin — or pass `--site-url` / `--site-name` to `mechanica export` — and the export injects the tags nobody should author by hand (`applySeoTags` in `mechanica-shared`'s `seo.ts`; a tag the template already contains is never duplicated): a directory-style **canonical** link + **`og:url`** per page, **absolutized social-image URLs** (root-relative `og:image`/`twitter:image` content breaks link previews otherwise), **`rel=prev/next`** + an automatic **"— Page N" title suffix** on pagination variants (skipped when the template references `page.pagination`), **WebSite JSON-LD** on `/` (needs `siteName`) and **BreadcrumbList JSON-LD** from the folder trail (named by page editor labels). It also emits **`sitemap.xml`** (with `<lastmod>` from the page file's mtime, overridable via frontmatter `meta.lastmod`) and a default **`robots.txt`** pointing at it (a `public/robots.txt` wins). Frontmatter **`meta: { noindex: true }`** adds a robots meta and drops the page from the sitemap; `/404` is noindexed automatically. Everything Vite copied from **`public/`** (favicon, fonts, verification files) ships with the export. The export also **lints layouts and the 404**: the SSR entry exports `layoutNames` (the `defineMechanicaApp({ layouts })` keys), and a page whose `layout:` frontmatter names an unknown layout warns with the fallback + declared names (once per logical page; skipped on pre-layouts bundles), plus a warning when no `/404` page exists (static hosts show their own error page otherwise). It also runs a **SEO lint** over each rendered page — empty/missing title or meta description, h1 count, `<img>` without alt, duplicate titles across pages — as warnings, like the link validator. The **image field** carries `alt` (authored in the editor) plus intrinsic `width`/`height` and — for images ≥256px — a ~24px **LQIP data URI** in `previewSrc`, captured on upload *and* on library picks (client-side canvas decode: `analyzeImageFile`/`analyzeImageUrl` in `editor/lib/image-size.ts`). **Preview blobs never live in `.page.md`**: they're stored in the **image manifest** (`.mech/images.json`, keyed by asset filename — one entry per asset however many pages use it). The dev server harvests data-URI previews out of incoming saves into the manifest (`harvestImageMeta`) and injects them back when building state (`fillImageMeta`); the export does the same (`backfillImageMeta`), so page files stay human-readable while rendered HTML gets the inline blur-up. The manifest is filled three ways: editor uploads/picks, **`mechanica images`** (headless — analyze everything under `.mech/assets`; how Claude generates previews for hand-authored pages, needs `sharp`), and export-time backfill via the **optional `sharp` dependency in the site's project** (`vite/dev/image-preview.ts`, resolved from the project root — never a mechanica dependency; without it the export warns with a hint when images lack metadata). Blocks render the value with the **`<Image>` component** (`import { Image } from 'mechanica'`, `src/core/image.ts`): alt + dimensions (no layout shift), `loading="lazy"` + `decoding="async"`, the LQIP as a blurred background until the real image loads, and an `eager` prop (`loading="eager"` + `fetchpriority="high"`) for above-the-fold heroes — dev-app's Banner is the reference. Give image-bearing blocks a data-URI image in `previewData` so previews stay self-contained (Banner again). Dev injects **no** SEO tags (templating context is identical though — `{{ site.url }}` resolves in dev).

**Focal point & crop (non-destructive).** The image value also carries an optional **focal point** (`focalX`/`focalY`, 0..1) and **crop** (a normalized `crop` rect over the original + a baked-down `croppedSrc`/`croppedWidth`/`croppedHeight` derivative). Both are edited in one **`ImageCropDialog`** reached from the image field's **Position / Crop** action: a stage over the original with a draggable focal dot, plus a resizable crop frame when the field opts in. A field opts into cropping with a **`crop` annotation** on its schema — `{ type: 'image', crop: { width, height } }` (aspect-locked to `width/height` and downscaled into that box), `{ aspect }` (ratio only) or `crop: true` (free) — read off the unfolded schema by the editor (`resolveCropConfig`); without it the dialog still offers focal-point editing. It's **non-destructive**: the original `src` + `crop` params stay on the value so a crop is always re-editable. The derivative is produced **client-side** (`renderCrop`, canvas, in `editor/lib/image-size.ts`; geometry helpers in `editor/lib/image-crop.ts`) and uploaded as a **derived asset** — a deterministic `<name>.crop-<hash>.webp` in `.mech/assets` (`saveDerivedAsset`, `x-derived-asset` upload header) that `listImages` hides from the picker and `isDerivedAsset` excludes from the export's orphan warning, but which the export copies + URL-rewrites like any upload (`generatePage`'s `collectFiles` rewrites `croppedSrc`). `<Image>` renders `croppedSrc` (and its own dimensions) in place of the original and emits the focal point as `object-position`; **`imagePosition(image)`** (exported from `mechanica`) formats the focal point as a CSS position string for blocks that paint an image field as a `background-image` (the feature's original motivation — `background-position`).

## Queries & pagination

`usePages(filter)` lists the site's pages — `folderName`, embedded `data` hooks, `sort` by `'name'`/`'path'`/a data field (`'postMeta.date'`), `limit`. `usePagination({ …, pageSize })` returns a reactive pager (`items`/`page`/`pageCount`/`total` + `pathFor(n)`/`prevPath`/`nextPath`). `useFetch({ url })` fetches external JSON — always **server-side** (dev server proxies, export bakes at build time). One **query engine** lives in `mechanica-shared` (`query-engine.ts`, pure over a `QuerySource` interface) with three callers: the dev server (`GET /@mechanica/query`, live against `.mech`; the generated dev entry passes `resolveQuery`), `mechanica export` (resolved at build time, memoized per key across the run, baked into `window.state.query` so the production client hydrates synchronously with no refetch), and the future hosted backend. The SSR contract is `render(state, { resolveQuery }) → { html, query }`.

**Pagination produces real pages.** At export, a page whose paginated query has N chunks also renders `/path/2` … `/path/N` — each a real HTML file with its own slice and `state.page.pagination`, present in the sitemap; a genuine page already at a variant path fails the export loudly. Dev serves variant URLs virtually: `buildPageState` maps `/blog/2` to the `/blog` page plus pagination context (`page.path` stays the base, so editing a variant edits the real page), and `mechanica shot /blog/2` works. A folder's own index page is excluded from its `folderName` listing. Queries resolve at block mount (no live re-query when the store changes — reload to refresh); SPA/pager navigation re-runs them, because `<Content>` keys blocks by pagination page (variants share content-node ids) and the router applies the target page's `page` meta + baked `query` results before the content swap. Reference demo: dev-app `/blog` — `BlogList.vue` (folder-scoped, pager UI), `src/data/post-meta.ts`, nine posts under `.mech/pages/blog/`.

## Data scoping

`defineData` entries carry a `scope`: `'site' | 'folder' | 'page'`. On save the dev server **splits** the data by scope (`data-store.ts` `splitDataByScope`): site → `.mech/data.json`, folder → `.mech/folders.json` (keyed by folder), page → the page file. Dev inject and static export **merge** site + the page's folder data back over the page's own data, so a value is authored once and shared correctly. The editor's "Edit page data" window edits all scopes (sorted site → folder → page).

## Multi-language pages (i18n)

(Phases 1–3 + locale-aware queries + translation overlays are implemented, only minor polish deferred; the PLAN.md design doc has been removed from the repo.) **A locale is a dimension of a page, not a separate page** — one logical page (`/about`), one PagesDialog row; translations are sibling files switched *inside* the editor, mirroring how pagination variants and the composer's breakpoint mode work. Turned on by the plugin **`locales`** option (`{ default, all, labels? }` or a bare `['en','ru']`; a single locale = off, so existing sites are unaffected). The pure path math lives in **`mechanica-shared/locale.ts`** (`normalizeLocales`, `parseLocalePath`, `localePath`, `localeLabel`) — the default locale serves **unprefixed**, every other under a **`/<code>`** prefix.

- **Storage**: translations are sibling files `<name>@<locale>.page.md` (`about@ru.page.md`, `blog/index@ru.page.md`) — the codec/save/undo paths are unchanged and per-locale `draft` is free. `@` can't appear in a slug, so the split is unambiguous. All variant CRUD is in `pages-store.ts` (`getPagePath(…, locale)`, `variantFilesOf`, `translationsOf`, `createTranslation`, `deleteTranslation`; `savePage`/`pageVersion`/`setPageDraft` take a `locale`); delete/move/duplicate/rename **cascade** to every variant, and `listPages` never lists a translation as its own row (each base row reports `locales`).
- **Translation overlays (field inheritance)**: a translation file is **sparse** — it stores only the fields it actually changes and **inherits everything else from the default-locale page**, so an image/link/color authored once in the default locale flows into every language automatically (change it once, no re-translation). The pure, schema-free math is `mechanica-shared/translation.ts` (`mergeTranslation` read-time, `diffTranslation` save-time, over `mergeValue`/`diffValue` + block-tree `mergeBlocks`/`diffBlocks`), barrel-exported. Two rules, both "**base owns structure**": (1) **blocks match by `id`** — the base owns which blocks exist and their order, so a block added to the base appears in every locale (untranslated), and a translation can't introduce/reorder blocks (overlay-only blocks are dropped on read *and* save); (2) inside a block's `data`, **objects deep-merge** (an image's `alt` can be translated while its `src` inherits; a `smartLink`'s `title` while its `url` inherits) but **arrays and scalars replace wholesale** (rich text / a card list is atomic — inherited or overridden entirely, never interleaved). This *is* the "auto by field type" model — the JSON shape drives it, no per-field flag needed. `createTranslation` seeds an **empty** file (all inherited); `buildPageState` and export `readTranslation` overlay it on the base; `savePage(…, locale)` diffs the editor's full content against a base normalized the same way (defaults + image meta filled, LQIP stripped) so equal values collapse away. `.page.md` files stay short, readable, and a genuine "what did we translate?" diff. **Backward-compatible**: an old full-copy translation still renders (every field present = override) and sparsifies on its next save.
- **Routing/state**: `buildPageState(mechDir, url, config)` strips the locale prefix *before* the pagination check (so `/ru/blog/2` composes), reads that locale's file (falling back to the default with `page.localeFallback`), and sets `page.locale`/`page.locales` + top-level `state.locales`. `page.path` stays **logical**. The middleware carries `locale` on `/save` + `/state`, adds `/@mechanica/pages/translation` (POST/DELETE), and rejects creating a page whose first segment is a non-default locale code.
- **Runtime**: `createMechanica` reads `state.locales` → `context.locales`; `useLocale()` (barrel-exported) gives `{ locale, locales, config, localePath }`; **`<Link>` auto-prefixes internal logical paths for the current `page.locale`** — pass `:locale="code"` to target a specific locale (language switchers). Blocks need no changes. `state.page.path` is always the **logical** path (dev *and* export), so `<Link>`/`usePagination().pathFor` prefix it once.
- **Locale-aware queries**: `usePages`/`usePagination` resolve against the current locale — the query engine's `QueryContext.locale` → `listPages(mechDir, { …, locale })` lists *only* pages translated to that locale and embeds each translation's data/name (a translated listing shows translated content and never links to an unrendered page). Dev passes `GET /@mechanica/query?locale=`; export's `resolveForPage(pageNumber, locale)` keys its cache per locale.
- **Export** (`cli/export.ts`): walks logical pages × existing translations (`readTranslation`) rendering each to `/ru/about/index.html`; **skips untranslated pages** (warns per locale); `applySeoTags`/`buildSitemap` (`seo.ts`) emit `hreflang` + `x-default` alternates and sitemap `xhtml:link`; `<html lang>` + `{{ page.locale }}` per page. `mechanica shot /ru/about` works (`shot.ts` resolves the logical path via the state endpoint).
- **Editor**: `LocaleSwitcher.vue` (pill beside `PageBar`) — switches locales via the in-place `navigation.switchPage(localePath(...))`, **creates a translation from the default** on demand, and flags a fallback view with an "untranslated" badge; `PagesDialog` shows per-locale coverage badges; `editor.ts` rides the `locale` on saves. Reads the config from `window.state.locales`. When editing a translation, `buildPageState` also ships the default-locale content as `state.baseContent` (dev only) → `store.baseContent`/`baseDataOf(id)`; the props panel (`SchemaForm`, top-level fields only) marks each field that **overrides** the default with a faint accent bar + a ↩ **reset-to-inherited** (restores the base value, which the sparse-save diff then drops), and `BlockSettings` shows a one-line "unedited fields inherit *{default}*" hint — the visible half of the overlay model.
- **Localized shared data**: a `defineData` entry with **`localized: true`** stores its site/folder value per locale in `data.<locale>.json` / `folders.<locale>.json` — holding *only* the entries that differ from the default (`data-store.ts` `mergeLocaleSiteData`/`mergeLocaleFolderData` diff-against-base + prune, so untranslated entries fall back and one reset to the default drops its override). Read merges the override over the base (`buildPageState` + export `readTranslation`); the editor splits the save by the flag (`editor.ts` `saveBody` → `siteDataI18n`/`folderDataI18n`) and the middleware routes it (base when editing the default locale). The Data window marks localized entries with a globe glyph + a language note — you edit the language you're viewing (no separate locale tab). Page-scoped data is already per-locale (it lives in the translation file).
- **Deferred** (minor polish): a staleness indicator (translation older than its base) and per-locale thumbnails.

**Node-side change** → needs `bun run build` + dev restart (plugin/middleware/entries/CLI/`seo.ts`); the browser entries (runtime/editor) are source-aliased.

## Conventions

TypeScript strict, ESM, named exports for the public API. **kebab-case** for TS modules, **PascalCase** for `.vue`. Tests are under each package's `test/` (mirroring `src/`), `*.test.ts` (Node) / `*.dom.test.ts` (jsdom), importing source via the `@/` alias; the mechanica Vitest config has two projects and a `mechanica-shared` → source alias (mirrored by tsconfig `paths`). Prefer pure, unit-testable helpers in `lib/` over logic embedded in components. English everywhere. `.vue` / `.css` / `.scss` / `*?svg-glob` imports are covered by `src/vue-shim.d.ts`; virtual modules by `src/virtual-modules.d.ts`.

When you change something, keep tests + typecheck green and add coverage. The legacy v1 lives in the sibling **`mechanics`** repo (reference only — don't edit it).
